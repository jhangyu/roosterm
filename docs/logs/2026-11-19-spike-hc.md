Findings that change the spec (details in `docs/hc-bridge.md`):
1. Keyboard input is **not** `terminal.send` (that method pastes text then presses Enter). Raw keys go as DATA frames on the attach channel. Resize is a RESIZE frame on the attach channel; there is no resize method.
2. After a core crash the **holder restarts the core by itself** (macOS: via a one-shot launchd job named after the holder PID; Linux: a new `hc-serve-*.service`). The socket file is re-created (new inode).
3. Crash leaves a **stale socket file** until the new core binds: dial returns `ECONNREFUSED`. Clean `hc server stop` removes the file: dial returns `ENOENT`. Both mean "hc not running".
4. `hc server stop` **ends every non-kept program** (`reason: "server_stop"`) and the holder. Never use it in deploy scripts or tests on a live host; use `hc server restart` (keeps programs).
5. Socket paths: macOS `~/.local/state/herdr-core/default/default.sock` (no `XDG_RUNTIME_DIR`); Linux `/run/user/<uid>/herdr-core/default.sock`. `HC_SOCKET` overrides.
6. The core keeps the environment it started with. A core started from inside a Claude Code session passed `CLAUDE_CODE_CHILD_SESSION` to `claude` ("Transcript saving is off" warning). Start the core from launchd/systemd, not from an agent shell.
7. Finished terminals stay listed (with `all: true`) for 24 h (`RETAIN_MS`, terminals.rs:9), and survive `hc server stop`.
8. File watch: Linux inotify gives `REMOVE` then `CREATE` for `default.sock` on core restart. macOS (fsnotify v1.10.1 / kqueue) gives `CREATE default.sock`, and also repeats spurious `CREATE` events for existing sockets on every directory change. The watcher must treat each event on the socket name as "try to dial once".

### Autostart (item 4)
- The `hc` CLI autostarts the core on first use (`client.rs:85-97`, `connect_starting`); `hc server start` is idempotent (second call RC=0, same core id).
- On macOS the core always moves itself into a one-shot launchd job (`macos_launchd.rs:1-2`, own coalition) unless `SSH_CONNECTION` is set. On Linux the core and holders run as transient systemd user services (`systemd.rs:1-4`); boot-time start without login needs `loginctl enable-linger` (hc prints this hint, `systemd.rs:453`).
- Recommendation for `deploy/`: macOS LaunchAgent with `RunAtLoad` that runs `/bin/sh -c 'hc server start && exec roosterm serve'`; Linux: `herdr-core.service` (user, `Type=oneshot`, `RemainAfterExit=yes`, `ExecStart=hc server start`) plus `roosterm.service` with `Requires=`/`After=herdr-core.service`. Roosterm itself never starts hc (contract criterion 6).
- Not live-tested: installing the LaunchAgent / user units themselves (no persistent changes to the user's launchd in this spike).

## Install (both hosts, user-only, no sudo)

```
HC_VERSION=0.1.21 HC_INSTALL_DIR=$HOME/.local/bin sh scratch/research/herdr-core-src/distribution/install.sh
```
The script is the repo's official installer (clone HEAD c751780); it fetches `https://releases.herdr.dev/core/0.1.21/manifest.json`, verifies sha256 (macOS-aarch64 `1ab38dd9…ffed`, linux-aarch64 `e844a2bf…529a`) and on macOS verifies the codesign identity `dev.herdr.core` / team `2W9652Q7QR`.
- macOS: `RC=0`, "hc 0.1.21 installed as Herdr Core.app"; `~/.local/bin/hc -> ~/.local/share/herdr-core/current/Contents/MacOS/herdr-core`; `hc --version` → `hc 0.1.21`.
- Linux: `INSTALL_RC=0`, "hc 0.1.21 installed into /home/jhangyu/.local/bin/herdr-core".
